# v3.2.2

Critical fix: plugin failed to load on current OpenCode hosts (unbound SDK log method)

A user-reported `/flow-auto` failure ("flow_status is not available in this environment") traced to plugin load, not project config. The OpenCode host logs showed `failed to load plugin path=opencode-plugin-flow@3.2.1 error="Cannot read properties of undefined (reading '_client')"` on every startup. Plugin init detached the host log method (`const log = ctx.client?.app?.log`) and the generated SDK's `app.log` is a class method that reads `this._client` — called unbound, it throws on the first log call, OpenCode reports the plugin as failed, and the entire Flow surface (tools, config hook, skill sync) silently drops. The call was also shape-wrong: the SDK carries the entry in `options.body`, not as top-level fields. Logging now goes through a bound, fail-silent wrapper posting `{ body: { service: "opencode-plugin-flow", level, message } }` — host log transport failures can never break plugin init again.

Why no gate caught it: every harness faked `app.log` as a plain standalone function, which neither crashes when detached nor validates the payload shape. The install smoke, bundle sanity, and the dist-load test now drive plugin init through an SDK-shaped fake (a class whose `log` prototype method reads `this._client`) and assert the startup entry arrives with the right body.

The investigation also surfaced dev-environment pollution: bundle sanity and the dist-load test invoked the real plugin factory without sandboxing `$HOME`, so every `bun run check` synced dev-versioned (`version=0.0.0`) skills, commands, and agents into the developer's real `~/.config/opencode` — which is how machines ended up with current skill text while the real plugin had never successfully loaded. Both harnesses now use a temp home, as the install smoke always did.

Constraint: Host-provided client methods must be called through the client object, never detached — generated SDK classes bind state to `this`
Constraint: Anything in plugin init that talks to the host is best-effort and fail-silent; only Flow's own sync and registration may fail loudly
Rejected: Binding with .bind(app) at the call site | fixes the crash but keeps the wrong payload shape and leaves the next detached method one refactor away; the wrapper centralizes both
Rejected: Treating the log call as optional and removing it | startup logging is the only signal users have that the plugin loaded; the fix is to make it safe, not to remove it
Confidence: high
Scope-risk: low
Reversibility: clean — one wrapper function in the adapter plus harness-fake upgrades
Directive: Test fakes for host interfaces must mirror the host's real shape (class methods, payload envelopes), not the simplest thing that satisfies the call site
Tested: `bun run check` (typecheck, lint, build, full test suite incl. the new SDK-shaped client regression test, npm-tarball install smoke asserting startup logs through the SDK-shaped fake and the 3.2.2 README pin, bundle sanity with sandboxed HOME); architecture seams gate
Not-tested: A live OpenCode host restart against the published 3.2.2 (the failing host error signature and the SDK method shape were verified directly from the user's logs and the cached SDK source)
