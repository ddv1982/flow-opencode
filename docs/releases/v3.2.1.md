# v3.2.1

A missing Flow backend is now a stop condition in the skills, not a silent downgrade

A real `/flow-auto` run surfaced a degradation mode the skills had no instruction for. Commands, skills, and the reviewer agent are markdown files OpenCode discovers from disk, so they remain available even when the Flow plugin itself is not loaded (project-local `plugin` array overriding the global one, a failed install at startup, an older binary). In that state the model hit step 1 of the driving loop — `flow_status` — found no such tool, and improvised: it disclosed the failure, then carried on with an ad-hoc read-only review. The findings were decent, but no session, plan, validation evidence, or review decision was recorded — the run quietly defeated Flow's purpose while looking like success.

The fix is instructional, matching where the gap was. The `flow` driving loop's "Stop and ask the user" list now opens with the missing-tools case: stop, tell the user to check `opencode-plugin-flow` in the `plugin` array of `opencode.json` (noting that a project-local `plugin` array overrides the global one) and restart OpenCode, and never substitute an unrecorded workflow. `flow-plan`, `flow-run`, and `flow-review` each get a matching one-liner anchored to the first tool they need (`flow_plan_save`, `flow_run_start`, `flow_review_record`), because each skill can be entered directly through its slash command without passing through the driving loop — the reviewer agent file in particular exists on disk independently of the plugin.

No plugin code changes; the skills are the shipped artifact and re-sync on startup via the content-hash markers.

Constraint: Skills must instruct the failure mode at every independent entry point, not only in the driving loop — commands make each skill directly reachable
Constraint: Degraded operation that records no Flow state is prohibited by instruction, not merely discouraged
Rejected: Detecting the unloaded-plugin state in code | nothing plugin-side runs when the plugin is not loaded; the markdown surface is the only thing present, so the markdown must carry the instruction
Rejected: A single shared note only in the flow skill | /flow-plan, /flow-run, and /flow-review load their skills directly and would never see it
Confidence: high
Scope-risk: low
Reversibility: clean — four prose additions to skill files, removable independently
Directive: Any surface that remains available when the backend is absent must instruct what to do in that state; silence becomes improvisation
Tested: `bun run check` (typecheck, lint, build, full test suite, npm-tarball install smoke asserting the 3.2.1 README pin, bundle sanity); architecture seams gate
Not-tested: A live /flow-auto rerun in an environment with the plugin deliberately unloaded (the original failure transcript is the motivating evidence)
