# v3.2.0

Stale installs become visible: a passive update notice, the running version in `/flow-status`, and documented update steps

This release closes the silent-staleness gap in OpenCode's plugin distribution. OpenCode caches each plugin install per spec string under `~/.cache/opencode/packages/<spec>/` and never re-resolves it, so once a version is cached the user keeps running it forever with no signal that newer releases exist — we verified this directly when a `@3` range pin kept loading 3.0.0 after 3.1.0 shipped. Plugin startup now schedules a background check against the npm `latest` dist-tag and logs a one-line notice when a newer release exists, naming the exact pin to set and reminding that two restarts are needed.

The notice is deliberately passive. It is fire-and-forget after startup sync (never blocks init), uses a 3-second timeout, and is fail-silent on every error path — offline, registry down, malformed payload — because a courtesy notice must never become a startup failure. It only ever notifies: the user's `opencode.json` pin is their intent and is never rewritten, following the lesson from oh-my-opencode's auto-rewrite bugs (oh-my-opencode#1745). `FLOW_DISABLE_UPDATE_CHECK=1` opts out entirely; the test preload, install smoke, and bundle sanity all set it so no CI lane ever reaches the registry.

`flow_status` now surfaces the running plugin version in its install check (`details.pluginVersion` and the passing summary line). The running version is the one fact a stale install cannot hide, so the readiness check users already reach for answers "which version did OpenCode actually load?" directly. The README gains an "Updating" section documenting the exact-pin bump workflow (change pin, restart twice), the manual cache-clear required for range pins, and the opt-out — and the install pin freshness gate added after 3.1.0 enforces that the README pin matches `package.json` on every release.

Constraint: The update check must never block, delay, or fail plugin startup — every failure path resolves to silence
Constraint: The user's opencode.json pin is never modified; the notice reports the new pin string and nothing else
Rejected: Auto-rewriting the pin in opencode.json when an update exists | oh-my-opencode shipped this and walked it back after corrupted-config bugs; a config file the user owns is not a safe write target
Rejected: Blocking version check during plugin init | adds registry latency to every OpenCode startup for a courtesy message
Confidence: high
Scope-risk: low
Reversibility: clean — the notice is one isolated module wired by a single call in plugin init; removing the call removes the feature
Directive: Network calls from plugin startup must be fire-and-forget, timeout-bounded, and fail-silent; anything load-bearing belongs in a tool the user invokes
Tested: `bun run check` (typecheck, lint, build, full test suite incl. dependency-injected update-notice tests covering newer/same/older/unreachable/invalid-payload/opt-out paths, npm-tarball install smoke asserting the 3.2.0 README pin, bundle sanity); architecture seams gate
Not-tested: The live notice against the real npm registry from inside an OpenCode host (registry endpoint and payload shape verified by hand)
